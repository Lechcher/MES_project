# Design

## Context

See `proposal.md` — Why. The change must produce `AGENTS.md` (repo root, currently 0 bytes) as the repository's agent-guidance file, in the shape of `AGENTS_Example.md`. The example provides the target structure: a `# <Name> - Agent Guidelines` title, then `## App` (name, platform, directory), `## Stack` (a layer/technology table), `## Design` (a pointer to a design document), and `## Rules` (grouped, project-specific rules with sub-sections).

Constraints that shape the approach:

- The project is a **web** application, not the mobile app the example describes, so the App/Stack content is adapted while the section structure is preserved.
- The stack is discoverable from the repo: `frontend/` is Next.js 16 + React 19 + Tailwind CSS v4 + shadcn/Base UI + better-auth; `backend/` is Bun + Elysia + better-auth + Drizzle ORM; the API contract is GraphQL (`API_CONTACT_SPECIFICATION.md`); Biome (root and frontend) does linting/formatting; TypeScript throughout.
- Project doc conventions: standalone root Markdown files, English, tables and code blocks.
- `frontend/AGENTS.md` already exists but is generated by `next dev`; the root `AGENTS.md` must not touch it.
- No specs exist in `openspec/specs/`, and no code references `AGENTS.md` by path. This change declares `skip_specs: true`.

## Goals / Non-Goals

**Goals:**

- A single, concise entry-point guide that lets an agent orient in the repo in one read: what the app is, its stack, where the design lives, and the rules to follow.
- A structure that matches `AGENTS_Example.md` so the document is familiar and consistent with the team's conventions.
- Accurate, repo-grounded stack and rules — no invented tooling.
- Correct pointers to the existing source documents (design, architecture, process, data, API, Git) rather than duplicating them.

**Non-Goals:**

- No implementation, no code, no config change.
- No restatement of the full source documents; the guide summarizes and links.
- No change to `AGENTS_GIT.md` (still the Git source of truth) or to `frontend/AGENTS.md` (generated).
- No spec-level behavior is defined here (no `specs/` deltas).

## Decisions

### D1 — One standalone Markdown file at the repo root

`AGENTS.md` is a single self-contained Markdown document at the repo root.

- *Why:* the file already exists as an empty placeholder at that exact path, and agents load the root `AGENTS.md` by convention; a single file is easy to consume as agent context.
- *Alternatives considered:* a `docs/agents/*.md` split (rejected — no `docs/` convention and the placeholder path is fixed); editing `frontend/AGENTS.md` (rejected — it is generated by `next dev` and scoped to the frontend).

### D2 — Mirror the `AGENTS_Example.md` structure

Use the same top-level sections in the same order: title, `## App`, `## Stack`, `## Design`, `## Rules` (with grouped sub-sections under Rules).

- *Why:* user-specified ("structure look like `AGENTS_Example.md`"); consistency with the team's established agent-guide shape makes the document predictable.
- *Alternatives considered:* a bespoke structure (rejected — the user asked for the example's structure).

### D3 — Ground the stack in the repository

Populate the Stack table from what actually exists in `frontend/package.json`, `backend/package.json`, `backend/lib/auth.ts`, `biome.json`, and `frontend/biome.json` — never from the example's stack.

- *Why:* the example documents a different (mobile) stack; copying it would be wrong. The prototype is a web app.
- *Alternatives considered:* a stack-agnostic guide (rejected — the whole value of the Stack section is concrete orientation).

### D4 — Rules: inherit project-specific rules, point to `AGENTS_GIT.md`

The Rules section states the working rules that apply to this repo: plan-first and the `openspec` workflow; minimal diffs; `.env` handling; dependency policy; Git branching/review with a link to `AGENTS_GIT.md` rather than restating it; Biome formatting/linting; TypeScript; and preservation of the shared code vocabulary (ticket state codes `REQ`/`ACT`/`PEN`/`APP`/`REJ`/`CAN`/`OVERDUE` and leave codes `AL`/`UAL`/`SL`/`USL`/`PL`/`ML`/`CL`/`EL`/`LWP`/`TOIL`/`VTO`).

- *Why:* these are the rules a contributor needs and that the source documents establish. Linking to `AGENTS_GIT.md` avoids duplicating and drifting from the binding Git policy.
- *Alternatives considered:* embedding the full Git policy (rejected — duplication and drift; `AGENTS_GIT.md` is authoritative).

### D5 — Point to the design and system documents

`## Design` points to `DESIGN.md` for the visual theme and to the architecture/process/API/data documents for system context.

- *Why:* the example's Design section is a pointer, and the project already centralizes this material in dedicated documents; pointers keep the guide concise.

## Risks / Trade-offs

- **Drift from the codebase** → Mitigate by grounding the Stack table in the current `package.json`/config files and keeping the guide short; update it when the stack changes (a stated rule).
- **Duplication with `AGENTS_GIT.md` or `DESIGN.md`** → Mitigate with pointers instead of restated content.
- **Copying the example's mobile stack by mistake** → Mitigate by the explicit Non-Goal and D3.
- **Touching `frontend/AGENTS.md`** → Mitigate by scoping the change to the root file only and noting the frontend file is generated.

## Migration Plan

Not applicable — this is additive documentation with no runtime, data, or API migration. Rollback is `git revert`/deleting the added file content. The change is archived after review, per project workflow.

## Open Questions

- Whether additional per-directory `AGENTS.md` files (for example `backend/AGENTS.md`) should later be added is a deferrable follow-up; it does not change this document's structure or the task breakdown. Default: not in this change.
